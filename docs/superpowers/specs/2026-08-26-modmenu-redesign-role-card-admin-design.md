# 哈比列车抽奖补齐 Mod Menu 全量重设计与角色卡资产管理设计

**日期：** 2026-08-26  
**目标模组：** `habitrain_lottery`  
**目标版本：** Minecraft 1.21.1、Fabric Loader 0.18.2、Mod Menu 11.0.3、Java 21  
**选定方向：** A 版“运营控制台”  
**状态：** Mike 已确认页面架构、角色卡数据流及交互验证要求

## 1. 目标

从零重建 `habitrain_lottery` 的 Mod Menu 配置页面，使大量配置和运营功能具有统一、清晰、响应式的界面，同时在“玩家资产”中加入单个玩家的四类角色卡管理。

本次改造必须满足：

1. 保留奖池、经济倍率、奖励规则、画面主题、玩家资产、称号管理、皮肤内容、撰写邮件和高级 JSON 九类现有功能。
2. 保持现有配置 JSON 格式、服务端权限、配置存储位置和运营操作不变。
3. 玩家资产新增乘客、独立、中立偏杀手、杀手四类角色卡的查询、增加、减少和精确设置。
4. 不提供全体玩家批量修改角色卡的能力。
5. 在线与离线玩家均可管理；在线状态、服务端内存和世界存档必须一致。
6. 不把损坏或缺失的角色卡文件静默解释为权威的全零存档。
7. 在常见窗口尺寸、GUI 缩放、中文与英文下保持控件可达、文本可读和操作语义明确。

## 2. 当前问题与根因

现有 `LotteryConfigRootScreen` 是一个约 2166 行的单体页面，导航、渲染、控件创建、草稿应用和九个功能区全部耦合在同一个类中。它已经包含“玩家资产”页面，但这条链路只处理抽数：

- `PlayerAdminModels.PlayerRow` 只有玩家名、UUID、抽数、硬币、解锁数和在线状态。
- `PlayerListS2C` 因此不携带角色卡数量。
- `LotteryConfigRootScreen#buildPlayersTab` 只创建抽数批量与单人控件。
- `PlayerChanceModifyC2S` 和服务端 `handleChanceModify` 只识别抽数修改模式。

因此“无法设置玩家角色卡”不是已有按钮失效，而是玩家快照、客户端控件、网络请求和服务端处理均未接入角色卡能力。

## 3. 范围

### 3.1 包含

- 重建 Mod Menu 配置根页面和九个功能页面。
- 统一页面布局、导航、状态、保存操作、控件风格和键盘交互。
- 玩家资产页面的玩家搜索、列表、基础资产详情和角色卡详情。
- 玩家快照增加角色卡数量和角色卡存储状态。
- 单个在线或离线玩家的角色卡增加、减少和设定。
- OP、菜单访问门控、输入边界、限流和服务端错误返回。
- 中英文翻译资源。
- 纯逻辑、存储、网络编码和构建验证。

### 3.2 不包含

- 全体或全体在线玩家批量修改角色卡。
- 修改上游 `starrailexpress` 或只读的 `哈比列车dlc`。
- 修改角色卡使用、自选角色、阵营匹配、每日使用次数或抽奖发卡规则。
- 修改现有配置 JSON 的字段和结构。
- 修改邮件、称号、皮肤、备份等功能的服务端业务规则。
- 以网页风格替代 Minecraft 控件或依赖 Mod Menu 内部 GUI 类。

## 4. 页面架构

### 4.1 Mod Menu 接入

`ModMenuIntegration` 继续只实现公开的 `ModMenuApi#getModConfigScreenFactory()`，并返回新的 `LotteryConfigRootScreen`。Mod Menu 负责发现和创建页面，目标模组自身负责全部 Screen 实现。

根页面保留父 `Screen` 引用，关闭后返回调用它的 Mod Menu 页面。客户端类只从 `client` 或 `modmenu` entrypoint 加载，避免 dedicated server 加载 GUI 类。

### 4.2 控制台外壳

新的 `LotteryConfigRootScreen` 只负责：

- 顶部品牌标题、当前位置和连接/权限状态。
- 左侧分组导航。
- 当前功能页面的挂载与切换。
- 底部通用操作区。
- 页面尺寸变化、焦点恢复和父页面返回。
- 服务器快照版本变化后的刷新分发。

根页面不再直接实现九类业务编辑器。每个功能页面通过共同的页面接口接收内容边界、当前权限和状态发布器，并负责自己的控件、草稿、校验、渲染及滚动。

### 4.3 九个功能页面

导航顺序和分组固定为：

1. 抽奖配置
   - 奖池配置
   - 经济倍率
   - 奖励规则
   - 画面主题
2. 玩家与内容
   - 玩家资产
   - 称号管理
   - 皮肤内容
3. 运营工具
   - 撰写邮件
   - 高级 JSON

每个页面显示页面标题和一句主任务说明。页面切换时保留各自的选择、搜索、输入草稿和滚动状态，不因控件树重建而跳回开头。

### 4.4 建议类职责

- `LotteryConfigRootScreen`：控制台外壳和 Screen 生命周期。
- `ConfigSection`：功能页面接口，定义初始化、渲染、tick、输入路由、应用、校验、销毁和状态恢复。
- `ConfigSectionContext`：提供父 Screen、字体、内容边界、权限、网络请求和状态发布能力。
- `ConfigNavigationRail`：分组导航、选择态、hover/focus、旁白和窄屏入口。
- `ConfigStatusBar`：连接、OP、只读、脏状态、请求中、成功、警告和错误。
- `ConfigActionBar`：刷新、应用、保存、重载和返回；根据当前页面能力显示或禁用操作。
- `PoolsConfigSection`、`RatesConfigSection`、`GrantsConfigSection`、`ThemeConfigSection`、`PlayerAssetsSection`、`TitlesConfigSection`、`SkinsConfigSection`、`MailConfigSection`、`JsonConfigSection`：九个独立功能页面。
- `PlayerAssetMutationPolicy`：纯 Java 输入规范化、模式识别、角色卡类型验证和数值边界。
- `PlayerCardAdminService`：服务端在线/离线角色卡快照与修改。

现有 `ScrollableButtonList`、`ScrollablePanel` 和 `MultilineTextArea` 可在核对生命周期、焦点和渲染方式后继续复用；如果其现有契约不足，再做目标明确的修正，不复制 Mod Menu 内部类。

## 5. 布局与视觉

### 5.1 设计语言

- 使用深色 Minecraft 面板、克制的青色导航强调和琥珀色主要操作。
- 主要文字、次级说明、选中状态和错误状态具有明确层级。
- 不依赖颜色单独表达在线、只读、成功或错误；同时使用文字、符号和形状。
- 主要控件优先使用 Minecraft 原生按钮、输入框、Tooltip、焦点和旁白能力。
- 自定义绘制只负责面板、分隔、强调条和状态背景。

### 5.2 响应式规则

布局按 GUI 逻辑宽度而非物理分辨率切换：

- 宽屏：固定左侧导航，右侧内容；玩家资产为玩家列表和详情双栏。
- 中屏：缩窄导航、间距和次要按钮文字，但保留主操作和页面说明。
- 窄屏：导航折叠为单页入口；玩家资产使用“玩家列表 → 玩家详情”的分步导航。
- 高度不足：顶部和底部固定，内容区独立滚动；底部操作不得被挤出屏幕。

布局使用统一 token：安全边距、栏间距、标准行高、标题区高度、底栏高度和分组间距全部由内容矩形推导，不散落坐标魔法数字。

至少检查 854×480、1280×720 和更宽窗口，并覆盖常用 GUI scale。检查对象是 Minecraft 实际 GUI 逻辑尺寸下的控件边界和可达性。

### 5.3 渲染与生命周期

- 构造器只保存父页面和必要依赖，不读取窗口尺寸或创建控件。
- `init()` 根据当前 `width`、`height` 计算布局并注册控件。
- 一个控件只能由 `super.render` 或页面手动渲染其中一种路径绘制，禁止重复渲染。
- 背景只绘制一次，Tooltip 在最上层绘制。
- 页面重建时恢复当前分类、玩家 UUID、搜索文字、列表滚动、详情子页和未提交输入。
- `removed()` 释放页面拥有的监听器或资源。

## 6. 保存和状态语义

其他功能沿用现有业务语义，但在页面中显式表达：

- “应用”：把当前配置页面的输入校验后应用到客户端内存，不写服务端磁盘。
- “保存到服务器”：先应用当前页，再提交完整配置或对应的称号模板保存请求。
- “重载磁盘”：放弃内存修改并请求服务器重新读取磁盘配置。
- 页面切换：按现有行为应用当前配置页输入到内存，再进入目标页面。
- 玩家资产、玩家称号操作、皮肤重新注册、邮件入口和备份操作继续使用即时提交或即时动作语义。
- “返回/Esc”：返回父 Mod Menu 页面；页面会清楚标识尚未保存到服务器的内存修改。

底部操作区根据当前页面能力显示：没有配置保存行为的即时操作页不显示无意义的“应用”或“保存到服务器”。

状态栏至少支持：

- 离线本地浏览。
- 已连接、等待 OP 状态。
- OP 可编辑。
- 非 OP 只读。
- 当前为未授权访问。
- 有内存修改但尚未写入服务器。
- 正在请求、提交成功、提交失败。
- 输入错误、角色卡存档缺失或损坏。

## 7. 玩家资产页面

### 7.1 页面结构

宽屏玩家资产页包含：

1. 页面标题和“修改即时提交”说明。
2. 刷新玩家列表和创建备份操作。
3. 左侧玩家搜索与列表。
4. 右侧玩家摘要、基础资产子页和角色卡子页。

玩家搜索同时匹配玩家名和 UUID，不区分大小写。列表显示在线/离线文字和符号、玩家名、抽数与硬币摘要。选择通过 UUID 保持，不依赖过滤后索引。

“基础资产”保留现有抽数单人增加、减少和设定。现有全体在线抽数操作保留，因为它属于原功能；角色卡子页不出现全员操作。

### 7.2 四类角色卡

角色卡列表固定显示：

| 规范键 | 中文名称 | 用途 |
|---|---|---|
| `civilian` | 乘客角色卡 | 乘客阵营角色 |
| `neutral` | 独立角色卡 | 独立/普通中立角色 |
| `neutral_for_killer` | 中立偏杀手角色卡 | 与杀手侧关联的中立角色 |
| `killer` | 杀手角色卡 | 杀手阵营角色 |

实际枚举与 `questKey` 以运行时 `FactionCardType` 为准；服务端只接受上述四种非 `NONE` 类型。

每一行包含：卡片名称、当前数量、步进输入、减少、增加和设为。默认步进为 1。数值输入只接受十进制整数。

- 增加/减少：单次 delta 限制为 `-1000..1000`，0 不发送。
- 设为：目标数量限制为 `0..100000`。
- 服务端再次验证全部范围；客户端限制不是安全边界。

### 7.3 存储状态

玩家快照为角色卡增加明确状态，不用空 Map 混淆不同情形：

- `ONLINE_LIVE`：在线玩家，数量来自 `BackpackManager.getCards(player)`。
- `STORED`：离线玩家，数量来自可读取的 `LocalBackpackStore`。
- `MISSING`：离线玩家尚无角色卡文件；页面显示尚未建立记录，首次有效设置会创建完整记录。
- `CORRUPT`：主文件和备份均不可读取；页面显示错误并禁用角色卡修改，服务端拒绝覆盖。

快照中的卡片 Map 使用规范的小写 `questKey`，缺失的合法键在可读取状态下补为 0，未知键不作为可编辑角色卡显示。

### 7.4 在线修改

在线玩家修改时：

1. 服务端读取 `BackpackManager.getCardCount(player, type)`。
2. 按 add 或 set 模式计算目标和 delta。
3. 调用上游公开的 `BackpackManager.addCard(player, type, delta)`；该 API 会把结果限制为非负数并标记内存状态 dirty。
4. `BackpackManagerMixin` 的现有持久化注入把当前枚举 Map 写入世界角色卡 JSON。
5. 调用 `BackpackManager.resend(player)`，立即同步玩家客户端背包。
6. 向管理员返回成功消息并刷新玩家快照。

这与上游 `BackpackCommand` 的 ADD、REMOVE、SET 行为一致，不直接操作上游私有缓存。

### 7.5 离线修改

离线玩家修改时：

1. 调用 `LocalBackpackStore.loadResult(uuid)`。
2. `CORRUPT` 直接拒绝，不写回。
3. `STORED` 复制现有 Map；`MISSING` 从四类合法卡的默认全零 Map 开始。
4. 只修改目标规范键，按范围夹取结果并保留其他键。
5. 使用 `AtomicJsonFiles` 支持的 `LocalBackpackStore.save` 原子写入。
6. 成功后刷新玩家快照；失败则返回具体错误并保留客户端输入。

玩家在操作过程中上线时，服务端在执行请求的同一线程重新查询在线玩家，在线则走在线路径，避免同时修改离线文件和活跃内存。

## 8. 网络和权限

### 8.1 玩家快照

`PlayerAdminModels.PlayerRow` 增加：

- 角色卡存储状态。
- 四类角色卡数量 Map。

服务端构建玩家列表时，先保留当前 `PlayerLotteryStore#listPlayers` 的玩家集合和基础资产，再由 `PlayerCardAdminService` 补充角色卡视图。角色卡读取错误不能导致整个玩家列表请求失败；该玩家显示为错误状态并禁止改卡。

### 8.2 修改请求

新增独立角色卡管理 payload，而不是在 `PlayerChanceModifyC2S` 中混入字符串模式：

- `targetUuid`：目标 UUID。
- `questKey`：四种合法角色卡类型之一。
- `operation`：`ADD` 或 `SET`。
- `value`：delta 或目标数量。

客户端只允许一个角色卡修改请求处于待确认状态。服务端响应后解除锁定并刷新玩家列表；网络失败或超时不乐观更新显示数量。

### 8.3 服务端防线

服务端处理顺序：

1. 检查发送者存在。
2. 执行角色卡修改专用限流。
3. 检查 OP 权限。
4. 检查 `MenuAccessBridge` 对应的服务端访问门控。
5. 解析 UUID。
6. 验证枚举操作、角色卡类型和数值范围。
7. 在服务器线程执行在线或离线修改。
8. 返回结果并按成功情况刷新快照。

客户端只读控件、隐藏按钮和 Tooltip 仅改善体验，不替代服务端检查。

## 9. 输入、错误和可访问性

- 无效输入在对应输入框附近显示原因，并禁用相关提交按钮。
- 禁用控件提供 Tooltip 或邻近说明，例如“需要服务器 OP”或“角色卡存档损坏，已禁止覆盖”。
- 网络请求中显示进行中状态并阻止重复提交。
- 请求失败保留玩家选择、搜索、步进值和待设置值。
- 所有图标按钮具备可见文字或 `Tooltip`、可理解的 narration 和 hover/focus 状态。
- Tab 顺序与视觉顺序一致；列表支持方向键，按钮支持 Enter/Space，Esc 返回。
- 在线/离线、启用/禁用、成功/错误不只依赖颜色。
- 长名称和长翻译先测量，再换行或省略；完整内容放 Tooltip。
- 所有用户可见字符串使用翻译键，新增完整 `zh_cn` 和基础 `en_us` 文本。

## 10. 测试策略

### 10.1 单元测试

测试先于生产实现，至少覆盖：

- 玩家快照 JSON 能往返四类角色卡和存储状态。
- 四个规范 `questKey` 与 `FactionCardType` 的映射。
- `NONE`、未知键、未知操作和无效 UUID 被拒绝。
- ADD 的 ±1000 边界、SET 的 0..100000 边界和负数结果归零。
- 离线已有文件只修改目标卡并保留其他卡。
- 离线缺失文件首次设置会创建完整四类记录。
- 离线损坏文件拒绝覆盖。
- 在线 set 通过当前值计算 delta，并触发内存更新、持久化和 resend 的服务边界。
- 玩家搜索同时匹配名称和 UUID，并能按 UUID 保持选择。
- 响应式布局计算在宽、中、窄尺寸下不产生负宽度或内容越界。
- 非 OP 或访问门控失败时修改被拒绝。

涉及 Minecraft/Fabric 静态启动的部分通过纯 Java policy、数据源接口和窄适配器隔离，普通 JUnit 不直接启动 Minecraft 客户端。

### 10.2 源码和资源检查

- `fabric.mod.json` 仍由正确的 `modmenu` entrypoint 打开配置页。
- 客户端 GUI 类不被公共或服务端 entrypoint 直接加载。
- 所有翻译键在 `zh_cn` 和 `en_us` 中存在。
- 控件没有同时注册为自动渲染并被手动画第二次。
- 页面切换、重建和关闭不会残留旧控件或监听器。

### 10.3 构建和交付

1. 运行相关定向测试并观察每个回归测试的 red/green 过程。
2. 运行完整测试。
3. 在目标项目执行 `./gradlew build`。
4. 检查 remapped JAR 中的类、payload、语言文件和 Mod Menu entrypoint。
5. 将生成的 release JAR 复制到 `D:\Backup\mc mod\临时`。
6. 计算并比较构建产物与交付 JAR 的 SHA-256。

构建、测试和 JAR 检查只证明静态逻辑与打包结果，不等同于游戏内视觉、键鼠操作、多人同步或 dedicated server 实测。未进行的验证必须明确报告。

## 11. 完成标准

- Mod Menu 能打开新的 A 版运营控制台并正确返回父页面。
- 九类现有功能均可到达，原配置和运营功能未被移除。
- 玩家资产能显示在线和离线玩家的四类角色卡状态。
- OP 能对单个玩家增加、减少和设定四类角色卡。
- 页面不存在角色卡批量全员修改入口。
