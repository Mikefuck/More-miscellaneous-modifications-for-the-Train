# 皮肤身份暴露排查与修复方案

本次已修改背部分类的“默认外观”图标为原版屏障。以下是源码排查结论与建议，尚未实施防暴露逻辑，也未进行多人游戏内复现。上游 DLC 仅用于参考。

## 已确认的逻辑缺口

### 1. 背饰跟随真实玩家，没有跟随当前显示身份

`client/BackSkinClient.java:38` 的 `appearanceFor` 处理完衣柜预览后，直接读取 `EQUIPPED.get(player.getUUID())`。因此 A 伪装成 B 时，背饰仍读取 A 的装备。

上游 `io/wifi/starrailexpress/hat/HatEquipmentApi.java:185` 已提供 `resolveDisplayedOwnerUuid`，通过 `OnResolveDisplayedSkinOwner` 解析显示身份。默认解析器覆盖变形者、嬉命人、窃皮者、阿蒙、双重人格和洗牌观察等情况。背饰当前没有使用这条路径。

### 2. 背饰没有接入匿名皮肤的隐藏规则

`client/render/BackSkinLayer.java:28` 只检查 `isInvisible()` 和 `isSpectator()`。普通隐身与旁观者已有保护，但 DISGUISE、疯魔皮肤、固定职业皮肤、亡命徒统一皮肤、难民旁观视角等皮肤替换不一定属于这两种状态，仍会进入背饰渲染。

上游 `HatEquipmentApi.getDisplayedHatSkinName` 已对 DISGUISE 和固定皮肤替换做隐藏处理。注意：`resolveDisplayedOwnerUuid` 本身不包含这些隐藏判断，单独调用它仍不能修好匿名外观暴露问题。上游固定皮肤隐藏判断目前是私有方法。

衣柜的 `WardrobeExtras.cycleHatMode` 修改的是上游帽子配置；它目前没有控制背饰。若用户期望“隐藏外观”同时控制背饰，需要明确增加对应设置或统一控制，而不能假定帽子选项已经覆盖背饰。

### 3. 武器等物品外观按真实账户装备，与显示身份无关

`bridge/InventorySkinApplier.java:37` 使用真实玩家 UUID 读取装备偏好，再把 `habitrain_lottery:skin` 写入背包物品。`client/SkinClient.java:86` 和 `mixin/client/IndependentSkinRendererMixin.java` 根据该组件直接选择模型，没有当前显示身份信息。

因此即使身体皮肤已替换，独特的刀、枪、球棒等外观仍可能让旁人认出本人。仅修背饰无法消除这些识别线索。仅在角色切换时强制刷新背包也不够：现有应用器刷新后仍会写入真实账户的外观。

## 推荐方案：统一解析显示身份，保持账户装备不变

在抽奖补齐的 `bridge` 层建立统一外观策略，客户端按“被渲染玩家 + 当前观察者”解析以下结果，再由背饰、帽子接入方及手持物品共用：

| 显示状态 | 外观策略 |
| --- | --- |
| 普通状态、大厅 | 使用本人装备 |
| 伪装成其他真实玩家 | 使用目标玩家外观；缺数据时隐藏背饰或使用默认物品外观 |
| DISGUISE、固定匿名皮肤、需要遮蔽身份的角色状态 | 隐藏个人背饰、帽子；物品仅去掉个人皮肤，保留原物品 |
| 隐身、旁观者、上游取消整个人物绘制 | 遵循现有不可见规则 |
| 衣柜预览 | 在预览作用域内展示选中外观，不影响世界状态 |

该策略应区分“显示本人”“显示目标”“匿名隐藏”，避免把“没有替换目标 UUID”误认为“可以显示本人外观”。应按当前观察者解析，兼容洗牌或精神状态造成的视角差异。

### 背饰的实施位置

让 `BackSkinClient.appearanceFor` 在衣柜预览之外先解析策略，再按显示身份读取外观；在匿名隐藏状态直接返回空。目标背饰缺少同步数据时，不得回退到真实玩家背饰。

同步也需要配套调整：`skin/BackSkinNetwork.java:35` 目前只向追踪者发送装备；停止追踪时还会删除该 UUID 的缓存。伪装目标可能已离开观察范围。完整的目标外观复制需要独立的在线外观目录或目标快照，并区分“明确未装备”和“尚未收到数据”。仅替换查询 UUID 可先阻止自己的背饰泄露，但不能保证目标外观始终完整。

### 手持物品的实施位置

上游 `AllowItemShowInHand` 事件已经传入玩家和物品，可在客户端桥接处对**渲染用副本**移除或替换个人皮肤组件，不必修改上游源码。需核对事件的先后顺序及现有物品替换监听器，确保不影响手铐、隐形物品和角色专属物品。

不要直接清除账户装备，也不要修改正在保存或用于游戏逻辑的真实背包物品。这样变身结束后外观会自然恢复，且不会干扰解锁与持久化。

### 需要同时验证的其他线索

- 投掷物：`bridge/SkinEffectRuntime.java:82` 会继承真实投掷者的手雷皮肤；单改手持渲染不会覆盖飞行中的手雷。是否将投掷物纳入防暴露，需要同步处理它的可见外观与特效。
- 定制音效、粒子：若也能唯一识别本人，需要遵循同一外观策略；只换模型仍可能留下声音或特效线索。涉及服务端特效时不能简单用客户端隐藏替代全部处理。
- 原版披风：上游 `MorphlingCapeRendererMixin` 存在目标皮肤缓存缺失时回退原披风的分支，可能形成独立识别线索，需要游戏内确认。帽子解析器不能直接控制原版披风。
- 身体皮肤替换由多个事件和 Mixin 分支实现，最终显示优先级还需在实际模组组合中验证，不能仅凭角色名称推断。

## 建议验证场景

1. A、B 装备明显不同的背饰和武器外观，A 变成 B；旁观客户端应看到 B 的外观或安全的默认外观，不能看到 A 的独特外观。
2. B 离开观察范围、目标外观包尚未到达、目标未装备背饰，分别验证没有回退到 A 的情况。
3. 测试 DISGUISE、固定职业皮肤、疯魔、双重人格、普通隐身和旁观者。
4. 测试切换角色、变身开始与结束、死亡重生、断线重连；原账户装备应完整保留。
5. 以不同精神状态的观察者同时观看同一玩家，确认各自外观策略与身体皮肤一致。
6. 测试衣柜预览及退出，确认预览没有写入世界缓存或改变真实装备。
7. 如纳入武器、手雷、音效、披风，分别验证相应识别线索，不以背饰测试替代。
